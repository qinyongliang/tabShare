# 架构与同步机制

[返回 README](../README.md)

## 组件

源网页继续在所有者的真实浏览器中执行 JavaScript，使用原有登录状态。扩展采集可渲染的 DOM 和必要画面，将访客的操作传回源标签页。访客不独立运行原网站。

```mermaid
flowchart LR
    Host[源浏览器与扩展] <-->|WebRTC：DOM、资源、输入、视频| Viewer[访客浏览器]
    Host <-->|鉴权与信令| Server[Go 服务]
    Viewer <-->|会话与信令| Server
    Server --- Relay[内置 STUN / TURN]
```

Go 服务管理配对、分享和信令，并提供内置 TURN 中继。WebRTC 不可用时，WebSocket/HTTP 继续提供应急同步和控制。

## WebRTC 与画面采集

DOM、本地表单输入与图片/字体优先走 WebRTC DataChannel；状态、输入和资源分开，16 KiB 分片、可靠有序传输，限制缓冲区和接收对象大小。远程模式使用视频轨道；DOM 模式仅在可见复杂区域需要时启动视频。CDP 视频来源会在源端将区域拼入较小画布后编码，访客按区域映射还原；覆盖关系复杂时切换整页画面。原生 tabCapture 轨道使用整页轨道，在访客端裁剪。没有音频轨道。

Chrome MV3 service worker 不提供 RTCPeerConnection，扩展在 offscreen document 中维护连接。手动共享当前标签页时尝试原生 `tabCapture`；Chrome 需要所有者先点击扩展，流 ID 也只能短时间内使用。自动重开的网址标签页及原生捕获不可用时，使用 CDP `Page.startScreencast` 连续获取共享标签页画面，送到 canvas 视频轨道再由 WebRTC 编码。没有合成帧的后台标签页使用自适应截图补充视频源：变化时目标 30 fps，不变时降低采样并跳过重复画面；浏览器自身限制后台页面脚本/动画时，无法强迫原网站按 30 fps 绘制。此路径在本机有 JPEG 解码及再次编码开销；JPEG 帧不经 Go 服务转发。它无法绕过 Chrome 捕获授权，扩展调试标识保持可见。关闭/暂停会话时释放视频；没有复杂区域的 DOM 模式停止视频采集。

优先直连，两端用 ICE/STUN 协商；内置 TURN 启用时也提供 STUN。默认额外 STUN 为 `stun:stun.l.google.com:19302`，可通过 `-stun` 改成自有服务或设为空（仅用内置 STUN）。直连失败时使用 TURN 中继，DOM DataChannel 和视频都适用，WebRTC 保持端到端加密；Go 的 TURN 不解密数据。初始化协商阶段或 WebRTC 不可用时，WebSocket/HTTP 应急传输也会经过 Go。页面显示当前 `P2P 直连`、`TURN 中继` 或 `WebSocket 兜底`。连接失败后每 5 秒重试，服务重新签发凭据给两端，避免无人值守运行超过 24 小时后使用过期凭据。

TURN 部署、鉴权和 TLS 参数见 [部署文档](deployment.md)。

## DOM 差异与资源传输

源标签页的隔离脚本用 `MutationObserver` 收集变化。相同节点的多次变化合并，默认最多每 200ms 发送一批。只计算受影响节点的样式，不每批扫描整棵 DOM；class/style 变化需要更新受影响子树。初次连接、导航和明确的重新同步发送完整结构；新访客通过 DataChannel 从源端合并缓存接收初始化快照；后续只收差异，不重新扫描整页，也不给已有访客重发全量。应急 WebSocket 通道使用服务端缓存。

常规 DOM 增量的软预算为每标签页 128 KiB/s。超过预算的批次会延迟下次同步，期间继续合并变化；初始结构不计入此持续预算。前台 WebRTC 视频目标最高 30 fps、4 Mbps，应用按访客显示尺寸主动缩放，并参考 RTT 和可用带宽限制码率；浏览器自身的拥塞控制继续生效。后台访客降到最高 2 fps、150 kbps，回前台自动恢复；所有访客都在后台时，CDP 来源也降低采集频率，DOM 更新适当降频。仅 WebRTC 未建立或失效时的应急截图最多 2 帧/s，软预算 64 KiB/s。预算是调度上限，单个批次、首次结构以及 WebSocket/JSON 开销可能产生短时突发。多个不同分享链接绑定同一标签页时，当前实现会分别转发，流量随链接数量增加。

图片、背景图和实际使用且已加载的字体通过源浏览器的资源缓存读取，必要时仅对已加载的 URL 使用源浏览器网络上下文补读，支持跨域和需登录的资源。资源优先通过独立的可靠 DataChannel 分片发送，DOM 增量中只携带短资源标识，访客验证 SHA-256 后生成本地 Blob URL。WebRTC 失效时才上传 Go 中继，服务器按 SHA-256 去重。资源使用独立 256 KiB/s 软预算，只按实际向各接收者发送的字节扣预算，缓存命中不等待。单个对象可短时突发，预算等待最长 30 秒；单资源上限 8 MiB、会话最多 256 项 / 32 MiB、服务器全局 128 MiB，源端和访客端也有 32 MiB 资源缓存上限。导航、最后一名访客离开、浏览器断开或撤销时清理服务器资源，资源不会落盘。浏览器无法读取或预算超出时自动整页画面降级。

静止页面不发送 DOM 数据，连接保活每 20 秒一次。CSS 动画使用可读取的 keyframes 在访客端本地播放，不采样每帧动画样式。JavaScript 动画产生的 DOM 变化按批次合并，可能降低动画流畅度。原页面复杂度、资源大小和网络延迟都会影响体验；这不是对所有网站都保持原生表现的保证。

## 渲染、压缩和背压

资源到达后只更新引用它的节点和 CSS 规则，同一批完成事件合并处理；不会重写所有表单和样式。资源请求去重，SHA-256 在源端复用，向多名访客传输时合并 Base64 转换和解码工作。

状态和资源使用独立通道，资源可能先于压缩 DOM 到达。访客保留最多 4 个待显示文档的资源，切换文档后清理已离开的版本，拒绝其迟到资源；暂存仍计入 32 MiB 缓存上限，避免导航时误丢图片和字体。

大于 16 KiB 且确实能缩小的状态消息使用 gzip；小输入消息直接发送，PNG/JPEG/字体等资源保持原始字节。压缩位于有序发送队列内，接收端按顺序解压，并限制解压后的大小。应急 WebSocket 可协商无上下文复用的压缩。服务端与扩展按当前版本一起更新。

输入按标签页排队，最多积压 256 个待执行操作。相邻待执行的鼠标移动可合并，按键、点击和导航保持顺序；超额访客断开后重新同步，不拖住其他标签页。网页提示的回答可直接解除源网页的阻塞。

DataChannel 采用缓冲区低水位事件恢复发送，每连接最多积压 24 MiB，同一模块实例内总计 64 MiB；长时间无法排空时断开并恢复同步。Go WebSocket 每连接最多积压 128 条 / 8 MiB，全局逻辑队列上限 64 MiB。广播共享已编码消息，连接关闭时释放预算。上述字节限制不是整个进程的内存上限；DOM、资源、解压缓冲、浏览器及系统开销另计。

会话请求体读取和 HTTP 响应均在全局状态锁外进行。持久化写入单独串行，成功落盘后才提交创建或撤销状态，失败不会改变当前访问权。
