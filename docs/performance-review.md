# tabShare 性能优化记录（2026-10-15）

基线：`330b4229beaee2cb139ee82a9c48d0c9c64172a2`（v0.7.1）。
本轮在独立副本完成，未修改原工作区、远端 main 或发布包。

## 结论

1. 不建议为了“虚拟 DOM”再加入 React/Vue。源端已经用 MutationObserver 标记变化，访客端有按 node ID 的状态缓存和定向 patch。这已经承担了增量渲染所需的主要职责；额外保留完整虚拟树会增加复制和内存成本。这里是对当前实现的判断，不是对框架性能的普遍结论。
2. 优先减少同步管线中不必要的对象复制、清理接收缓冲和缓存计账，再以真实浏览器的端到端延迟决定下一步。
3. 暂不把生产协议全面改成 Protobuf。原型的报文较小，但当前 JavaScript 实现的适配和编解码更慢；大包已经 gzip 和样式池化，收益不能按未压缩 JSON 体积计算。
4. Canvas、视频、不可镜像区域的局部 WebRTC 视频已经存在，不需要再造一套。普通静态图片应继续内容哈希去重、缓存和二进制资源传输；改成持续视频会损失清晰度并增加编码开销。

## 已修改并验证的代码

- `web/mirror.js`：仅在 patch 真正包含 style/attrs 时复制对应缓存。文本、输入值等稀疏更新复用未改变的映射；删除属性从缓存中清理，旧快照不被修改。
- `extension/peer.js` 与 `web/peer.js`：连接关闭时立即清空未完成分片，取消超时并解除 DataChannel 事件闭包。已排队解码仍正确归还计账，不提前投递、不产生负计数。
- `web/resources.js`：释放资源同时清空 sizes 和已使用字节计账。尚在异步执行的资源保留 reservation，直到原任务 finally 归还，避免重复扣减。
- 新增 4 项单元回归；两端协议文件保持逐字一致。

## 实测数据与范围

### 稀疏更新缓存微基准

命令：`node benchmarks/sparse-mirror.mjs`。
Node v24.19.0，先预热，再交替测试两版本，7 次取中位数；每次 20,000 个输入值 patch。
使用惰性 DOM 适配器，只测缓存/属性处理，不包含浏览器布局、视频或网络。

| 节点缓存样式字段数 | 修改前 ms | 修改后 ms | 样式复制次数：前 → 后 |
| --- | ---: | ---: | ---: |
| 0 | 3.157 | 3.516 | 20,000 → 0 |
| 20 | 3.455 | 2.832 | 20,000 → 0 |
| 100 | 5.578 | 2.942 | 20,000 → 0 |

有样式的样本改善；空样式样本略慢。不能把这组结果宣传为整个应用快了某个百分比，也没有测浏览器总内存下降量。

### 协议原型

`benchmarks/protocol.proto` 只是测试候选，不是生产协议；不覆盖全部 SVG、伪元素、输入、元数据和兼容性字段。
`benchmarks/protocol.mjs` 使用 protobufjs 8.8.1，在 /tmp 独立安装，无生产依赖变更。
比较包含 JS 对象适配成本，所有样本均先验证往返一致。gzip 使用 Node 同一实现比较体积，未把它当浏览器编解码时间。小包在生产中不压缩，表中 gzip 仅作体积对照。

| 样本 | JSON / Proto 原始字节 | gzip 后 JSON / Proto | JS 往返 JSON / Proto ms |
| --- | ---: | ---: | ---: |
| 输入 | 76 / 39 | 91 / 60 | 0.00087 / 0.00144 |
| 文本 diff | 108 / 40 | 124 / 61 | 0.00149 / 0.00294 |
| 20 节点样式 diff | 2,039 / 1,355 | 256 / 216 | 0.01993 / 0.04943 |
| 300 节点未池化初始化 | 42,651 / 32,691 | 2,701 / 2,645 | 0.35674 / 1.02577 |
| 300 节点池化初始化 | 25,624 / 13,559 | 2,545 / 2,257 | 0.21926 / 0.55537 |

池化初始化压缩后节省约 11%，这个原型往返却约为 JSON 的 2.5 倍。其他生成器、静态生成代码、实际网站数据可能改变结论；现在不足以证明全面替换值得。原始结果保存在 `benchmarks/results/`。

## 现有链路核对

- `dom-capture.js`：MutationObserver、dirty/priority/subtree 集合、按字段 difference、包内样式池化。
- `worker.js`：交互唤醒最短目标间隔 16ms；普通连续样式更新仍可能 200ms；保留字节预算。文档中“所有 DOM 最多 5Hz”的描述已落后于交互唤醒实现。
- `peer.js`：DOM、输入、资源三个可靠有序 DataChannel；16 KiB 分片；状态大包超过约 2 KiB 且压缩至少省 10% 才 gzip（旧架构文档写 8 KiB，需纠正）。
- `video-capture.js`：每标签页共享裁剪画布；多个复杂区域拼入画布后编码；原生 tabCapture 与 CDP 路径分开。
- 视频已有尺寸、码率、帧率、后台和网络质量自适应，不能把新版本现有能力算成本轮新增。

## 接下来优先验证的热点

- `capture()` 处理普通输入后仍会遍历全部 nodes 检查断开节点；可改成仅收到 removal 事件时扫描，必须覆盖 Shadow DOM、移动节点、body 替换和跨批次采集。
- `fallback()` 遍历所有节点寻找视频区域；可维护 unsupported/failed 候选索引，不能漏掉资源失败或布局/遮挡变化。
- 高频输入的 localEdit 为每次输入创建定时器；可按节点复用一个定时器，导航/移除时清理。
- 实时策略应使用有截止时间的短合并窗口，避免 debounce 被持续变化无限推迟；不要简单取消所有背压或把旧 diff 丢掉。

这些更影响 DOM/画面正确性的修改本轮未盲目落地，需浏览器回归后推进。
